## macOS Fontconfig 与实际 PDF 证据

2026年11月10日，对比用户提供的正常与异常PDF：均由 LibreOffice 26.8.2.2 AARCH64 生成。正常13页，含 ArialUnicodeMS 和 PingFangSC；异常11页，仅 LinuxLibertineG、FrankRuhlHofshi-Bold 和 Carlito。异常文件仍可提取中文，但渲染第一页仅见英文与来源路径，证明文件存在或文本可提取不足以验证显示正确。用户文件不入仓库。

修正 macOS 转换子进程的显式 Fontconfig 设置：继承可用字体规则并指定绝对系统字体目录、用户目录及可写缓存。配置继承与子进程环境隔离有合成测试。新增样本字体组合拦截，实际两份PDF分别被接受和拒绝，不将异常新文件替换到预览。该检测不覆盖所有字体与缺字情形。30项后端测试、13项前端测试及生产构建通过。修正既有DOCX测试夹具的ZIP时间戳，使原件字节比较稳定。macOS实际重新转换仍须用户本机验证，不能把Linux测试视为故障已消除。

同类实测参考：https://github.com/openai/codex/issues/32968 ，包含独立系统 LibreOffice 在 macOS 命令行转换时不加载 Fontconfig 规则的复现和显式 FONTCONFIG_FILE 处理方式。

## 自动转换字体配置继承

2026年11月10日，针对手动导出正常而自动转换缺中文的反馈，修正自动转换不继承日常字体配置的差异。选择性复制字体与语言设置及配置目录字体，保持独立临时配置；不复制宏或最近文档，不改源配置。26项后端测试、13项前端测试及构建通过，新增覆盖设置筛选、原配置不变、配置路径覆盖和无配置提示。Linux 上使用已安装 Noto CJK 字体实测合成中文DOCX，含分式及中文表格，转换PDF可提取中文并渲染检查。此证据不复现用户的macOS问题，不保证继承配置就能解决所有缺字；macOS实际试卷仍需重新生成验收。

## 原文预览重新生成

2026年11月10日，DOCX 原页增加重新生成入口。已有 PDF 时也会实际执行转换；重复请求去重，原 PDF 保留到新文件通过检查后原子替换。生成中与失败时仍可查看旧版，成功后按文件版本刷新 iframe 并禁止缓存 PDF。23项后端测试、13项前端测试及生产构建通过；回归覆盖重新入队、版本变化、失败保留旧PDF与源内容不变。真实浏览器与中文字体效果尚需本机验收。
